# Mark'd 站点代码审查：冗余、不合理实现与修改建议

审查日期：2026-11-11。范围是仓库内全部页面、样式、脚本、构建脚本和文档。本文只做分析，没有改代码。

站点是三页静态营销页（`index.html`、`about.html`、`privacy.html`），由一份 CSS 和一份拼接脚本 `assets/js/markd.bundle.js` 驱动。当前 bundle 与 `scripts/build-js.sh` 的源文件顺序一致，没有“源码和产物分叉”的现状问题。

## 结论

真正贵的问题不在“再抽一层公共组件”，而在三件事：

1. `assets/images/` 里约 **19.0 MB** 原图没有被任何页面引用，却会随 GitHub Pages 一起发布。
2. 暗色主题已经由页头脚本算好，导航插入时又用模块里的默认值 `light` 去换图，暗色用户会先请求到浅色图。
3. 主题、语言、字体的判断在三个 HTML 和 `theme.js` / `i18n.js` 里各写了一遍。繁体语言标签 `zh-Hant-TW` 这类值会落到简体。

其余问题主要是为一座三页站点准备的通用框架：性能监控、懒加载、图标库、工具函数库、组件配置层，调用方几乎不存在。删掉它们的收益是阅读成本和误用面，不是明显的加载时间。

下面的 ROI 按这个标准：

| 等级 | 含义 |
| --- | --- |
| 高 | 改动小，立刻减少体积、可见缺陷，或消除会继续分叉的逻辑 |
| 中 | 改动集中在一个模块，主要改善一致性和后续修改成本 |
| 低 | 整洁收益，可以顺手做，不必单开一轮 |

## 建议保留的部分

这些看起来像重复，继续保留比再抽象更合适。

- 导航和页脚用运行时插入，是在没有 HTML 模板构建的前提下共享两块 UI 的合理做法。不要为了两个按钮再引入组件框架。
- 首页和关于页把英文写在 HTML 里，同时在 `translations.js` 里再放一份。这是无脚本和爬虫时的正文，应该保留。
- 截图的 WebP 主图加 720 PNG 回退应该保留。README 写的支持范围包含 iOS Safari 12，该版本没有 WebP。
- 单文件 CSS 和语义色变量是对的。主按钮、导航下载芯片、页脚图标按钮外观不同，不应并成一个 class。
- `scripts/build-js.sh` 的拼接方式足够。不需要为这个仓库上打包器。

## P0

### 1. 站点目录里放着没有被引用的原图

**位置**

`assets/images/` 中这些文件没有任何 HTML、CSS、JS 引用：

| 文件 | 大小 |
| --- | ---: |
| `screenshot-light.PNG` | 5.5 MB |
| `screenshot-dark.PNG` | 5.4 MB |
| `Markd-iOS-Dark-1024x1024@1x.png` | 2.8 MB |
| `Markd-iOS-Default-1024x1024@1x.png` | 2.6 MB |
| `Collection-light.PNG` | 1.9 MB |
| `Collection-dark.PNG` | 1.8 MB |

页面实际使用的是 `*-240.png` 图标，以及 `*-720.webp` / `*-720.png`。未引用文件合计 **19,939,956 字节（约 19.0 MB）**，已引用图片合计约 **1.5 MB**。

**影响范围**

仓库克隆、GitHub Pages 发布源、任何能猜到路径的直接下载。页面不显示它们，但 Pages 以 `main` 为源时，目录里的文件都是公开资源。这是全库最大的体积问题，比全部 JS 加在一起还大一个数量级。

**ROI：高**

删除或移出发布目录即可，不改页面行为。720 PNG 回退和 240 图标要留下。

**最佳解决方案**

从发布目录移除这 6 个原图。需要留档时放到不会被 Pages 发布的位置（私有存储，或只发布构建产物的分支），不要放进 `assets/`。`scripts/optimize-images.py` 继续只处理 4 张 720 PNG。

`assets/images/README.md` 仍在说明 App Store 徽章和 TestFlight 徽章，和现在的文字按钮不一致，应改成当前文件命名规则，避免下次再把原图放回这个目录。

### 2. 主题模块用默认浅色去换图，页头已经算好的暗色被盖掉

**位置**

- 页头内联脚本：三个 HTML 的 `<head>`，根据 `localStorage` 和系统偏好设置 `data-theme`
- `assets/js/theme.js`：`currentTheme` 初始值是 `'light'`，`initTheme()` 不会在模块加载时执行
- `assets/js/components/index.js`：插入导航后立刻调用 `MarkdTheme.syncMedia()`
- `assets/js/main.js`：要等到 `DOMContentLoaded` 才调用 `MarkdTheme.init()`
- `index.html` 底部还有一份相同的换图脚本，在 bundle 之前把首页截图设对

**实际顺序**

1. 页头把 `<html data-theme>` 设成 `dark`。
2. 首页底部脚本按这个属性把截图设成暗色。
3. bundle 执行。导航插入后 `syncMedia()` 读取模块内部的 `currentTheme`，此时仍是 `'light'`，于是所有带 `data-src-light` / `data-src-dark` 的图（导航图标、首页两张截图）都被改成浅色地址。
4. `DOMContentLoaded` 之后 `initTheme()` 再改回暗色。

浅色用户看不出这个问题。暗色用户会多发一轮浅色图片请求；浅色图若已在缓存里，首屏有机会先闪浅色截图。

**影响范围**

三页的导航图标，以及首页 hero 和功能区截图。手动暗色和“跟随系统的暗色”都会中招，因为页头脚本是对的，被覆盖的是 JS 模块自己的默认值。

**ROI：高**

改动集中在 `theme.js` 和 `components/index.js` 的调用顺序，大约十几行。

**最佳解决方案**

主题的唯一初始来源用页头已经写上的 `document.documentElement.dataset.theme`。`syncMedia()` 只读这个属性，或在插入导航之前先跑 `MarkdTheme.init()`。`main.js` 里那份 `currentTheme` / `window.currentTheme` 影子状态可以去掉，按钮点击直接问 `MarkdTheme`。

首页底部那份换图脚本可以留着，用来在 bundle 到达前先放上正确的 hero 图。它和 `theme.js` 里的 `themedImageSrc` 是同一算法的两份实现，应抽成页头引导脚本里的一个函数，供底部脚本和 `theme.js` 共用，避免 fallback 规则以后只改了一边。

### 3. 主题、语言、字体的判断复制了多份，繁体检测会漏

**位置**

同一段 `localStorage` + `navigator.language` 逻辑出现在：

- `index.html`、`about.html`、`privacy.html` 的页头（各一份，约 30 行，含 Google Fonts 插入和 gtag 前后的固定头）
- `assets/js/i18n.js` 的 `initLanguage()` 和 `resetToAuto()`
- `assets/js/theme.js` 的 `initTheme()` 和 `resetToAuto()`

字体链接同样写了 4 次，而且繁体也请求简体字体：

`https://fonts.googleapis.com/css2?family=Noto+Sans+SC:wght@400;500;700&display=swap`

**行为问题**

语言判断是精确相等：

- `zh-tw`、`zh-hant` → 繁体
- 其余以 `zh` 开头 → 简体

因此 `zh-Hant-TW`、`zh-Hant-HK`（小写后是 `zh-hant-tw`、`zh-hant-hk`）会进简体。`zh-HK` 也会进简体。这段判断复制在 5 处（3 个页头 + `initLanguage` + `resetToAuto`），修一处不够。

页脚语言按钮的初始文字是「中」，而运行时标签是 `En` / `简` / `繁`。「中」对三种语言都是错的，会一直显示到 `updateLanguage()`。

**影响范围**

三页首屏语言、`<html lang>`、中文字体、页脚按钮。主题键名（`theme`、`theme_manual`、`lang`、`lang_manual`）也是同一协议的两套实现，以后改键名会只生效一半，出现“页头一种主题、点击后又跳回另一种”。

**ROI：高**

三页头现在各复制约 50 行（引导脚本、字体 preconnect、gtag、CSS）。引导逻辑收成一个同步脚本后，分叉风险消失。gtag 仍可留在各页，或一并放进这个文件。

**最佳解决方案**

新增一个在 CSS 之前同步加载的 `assets/js/boot.js`（不能 `defer`），只做四件事：读主题、读语言、设置 `data-theme` 和 `lang`、按语言插入字体。`theme.js` / `i18n.js` 启动时信任这两个 DOM 属性，不再重写检测。`resetToAuto()` 若没有界面入口就删掉；要保留就调用同一份检测函数。

繁体判断改为：语言标签以 `zh-hant` 开头，或为 `zh-tw`、`zh-hk`、`zh-mo`，使用繁体。简体用 Noto Sans SC，繁体用 Noto Sans TC。英文不要预连接 Google Fonts。

页脚 `.lang-text` 的初始值改为 `En`，或由 `boot.js` 写好，避免闪出「中」。

## P1

### 4. 五个脚本模块没有有效调用方

**位置与证据**

| 模块 | 体积（未压缩） | 实际情况 |
| --- | ---: | --- |
| `assets/js/utils.js` | 7.2 KB | 导出 10 个函数。生产路径只用到 `getNestedValue`（`i18n.js` 自己也有一份回退）。`supportsFeature` 只被下面的懒加载使用。`debounce`、`throttle`、`isInViewport`、`waitForElement`、`setNestedValue`、`safeJsonParse`、`getUrlParameter`、`formatFileSize` 无调用 |
| `assets/js/lazy-load.js` | 4.2 KB | 查找 `img[data-src]` 和 `[data-bg]`。页面用的是 `data-src-light` / `data-src-dark` 和原生 `loading="lazy"`。每次访问都会跑一遍空查询 |
| `assets/js/performance.js` | 4.9 KB | 使用已废弃的 `performance.timing`，只在 localhost 打日志。`timeToInteractive` 从未赋值。正式环境仅在加载超过 3 秒时 `console.warn`。不接入 gtag |
| `assets/js/icons.js` | 2.1 KB | `createIcon()` 无调用。`scan`、`camera`、`star`、`share`、`cloud`、`smartphone` 是旧功能卡图标。月亮、太阳、地球图标在页脚和 `theme.js` 里又手写了一遍 |
| `assets/js/error-handler.js` | 2.6 KB | 全局 `error` / `unhandledrejection` 再 `console.error` 一次。依赖检查在 bundle 同步执行后 100ms 跑，bundle 完整时必然通过 |

五个文件合计约 21 KB，gzip 后约 5 KB。当前 bundle 未压缩 93 KB、gzip 约 22 KB，其中文案占 26 KB。删掉这些模块，加载时间几乎不变。

**影响范围**

三页都会下载。风险是以后有人调用这些“看起来可用”的 API（例如给图片加上 `data-src`，和主题换图打架），或在 `utils.js` 修一个实际上没人用的函数。

**ROI：中**

删除本身很快，但要跟着改 `scripts/build-js.sh` 并重新生成 bundle。收益是维护面，不是性能。

**最佳解决方案**

从构建列表移除这五个文件。`i18n.js` 保留自己那 4 行的路径读取即可。主题按钮继续用现在的 SVG path，直到下面的图标项一起收口。不要用“以后可能用到”把它们留成公共库。

`MarkdPerformance`、`MarkdLazyLoad`、`MarkdUtils`、`MarkdIcons`、`MarkdErrorHandler` 在 `window.Markd` 上的入口一并删除。仓库内没有任何页面调用 `window.Markd` 或 `window.MarkdApp`。

### 5. 隐私页的数组正文没有静态英文，和其他页的策略不一致

**位置**

`privacy.html` 里这些节点是空的，正文只存在于 `translations.js`，要等 `i18n.js` 用 `innerHTML` 填上：

- `privacy.intro.content`
- `privacy.use.list`
- `privacy.security.content`
- `privacy.rights.content`
- `privacy.rights.list`

首页的理念段、关于页的使命和步骤，HTML 里已经写了英文段落或列表。字符串类文案（标题、单段）三页都有英文回退，和 `en` 文案一致，没有发现字符串漂移。

**影响范围**

`privacy.html`。脚本失败、脚本被拦截、或内联引导抛错时，这些小节只剩标题。首屏也会先空再填入。首页和关于页没有这个问题。

**ROI：中**

把现有英文数组抄进对应标签即可，不需要新系统。空节点是当时为了省事，和另外两页的做法分叉了。

**最佳解决方案**

隐私页按关于页的方式写下英文 `<p>` 和 `<li>`。`i18n.js` 在切换语言时仍整体替换这些节点。

渲染规则同时简化：数组放在 `ul` 上就生成 `<li>`，否则生成 `<p>`。现在还要看 key 名里有没有 `content` 或 `list`，并且 `parentElement` 是 `ul` 时也会包一层 `<li>`。当前数据碰巧都符合，这条规则是隐式契约。替换前对文案做文本转义，再把换行变成 `<br>`。文案现在是第一方字符串，转义是为了避免以后某句带 `<` 或 `&` 被当成 HTML。

### 6. 组件配置层和双全局命名空间超过了实际用法

**位置**

- `assets/js/components/config.js` 的 `getConfig()` / `mergeConfig()`
- `assets/js/components/index.js` 再读一遍 body 属性
- `assets/js/components/navbar.js` 和 `footer.js` 插入前又 `mergeConfig` 一次
- `assets/js/main.js` 同时挂了 `window.MarkdApp` 和 `window.Markd`

**实际用到的配置只有两个**

- `data-download-link`：首页 `#download`，内页 `index.html#download`
- `data-navbar-show-home`：关于页和隐私页为 `true`

`showBrand`、`showDownload`、`showLinks`、`showControls`、`showCopyright` 在三页上都是默认 `true`，没有任何页面关掉它们。

下载链接还绕开了这套通用解析：通用解析只认 `data-navbar-*`，下载地址却叫 `data-download-link`，于是 `index.js` 又手写了一次赋值。`showHome` 则被 `getConfig()` 和 `initialize()` 各读一次。

`MarkdApp` 的方法只是转发给 `MarkdTheme` / `MarkdI18n` / `MarkdIcons`。`error-handler.js` 检查 `MarkdApp` 是否存在，除此之外没有调用方。`toggleLanguage()` 会在三种语言间循环，界面用的是下拉菜单，这条路径没有入口。

**影响范围**

改导航或页脚的人要先理解三层合并，才能确定最终 href。行为上当前三页是对的，问题在于阅读成本和错误的扩展方式。

**ROI：中**

删掉配置模块、在 `index.js` 里直接读两个 data 属性，导航和页脚函数只接收已经算好的选项。对外只留 `MarkdTheme`、`MarkdI18n`、`MarkdInAppBrowser` 这三个确有调用的对象。

**不值得做的方向**

不要把“是否显示品牌、版权、链接”做成配置。三页都要这些。真有一天某一页不要页脚，删掉那一次 `insert` 即可。

### 7. 相似控件没有共用实现，失效别名还留在选择器里

**位置**

图标三套并存：

- `icons.js` 的 path 字符串（无调用）
- `theme.js` 的 `updateThemeButton()` 用 `innerHTML` 替换月亮/太阳 path，和 `icons.js` 的 `moon` / `sun` 重复
- `footer.js` 内联地球和月亮 SVG
- 首页 App Store 图标是页面底部的 `<symbol id="icon-appstore">`，理念链接的箭头又是另一段内联 SVG

按钮：

- `.btn-primary` 是真正的下载按钮，首页用了两次，标记几乎相同
- `.app-store-btn` 在 CSS 里整段复制了 `.btn-primary`（约 25 行），HTML 已无此 class
- `main.js` 和 `inapp-browser.js` 的选择器仍写着 `a.app-store-btn`
- 内嵌浏览器的 `.inapp-dismiss-btn` 再次手写了一套胶囊按钮尺寸、字号和颜色

内嵌浏览器颜色是第二套 token。`style.css` 在 1268 行另起一个 `:root` 和 `[data-theme='dark']`，把 `#1D1D1F`、`#F5F5F7`、`#0B0B0D` 再写一遍，对应已有的 `--text-primary`、`--btn-bg`、`--btn-fg`、`--bg-primary`。卡片圆角写死 `24px`，设计说明里的大圆角是 `28px`（`--radius-lg`）。

`getText()` 在 `inapp-browser.js` 里依次尝试 `getTranslation`、`t`（同一个函数）、再按顶层 key 读 `translations[lang][key]`。第三次查找看不懂嵌套 key。提示层节点本身已经带 `data-i18n`，语言切换时 `i18n.js` 会更新它们；`updateOverlayText()` 只在打开时需要。

App Store 地址写在首页两处链接里，应用 ID `6755139749` 又作为 `inapp-browser.js` 的解析失败默认值。

**影响范围**

首页两个下载按钮、页脚主题按钮、内嵌浏览器弹层。改图标或按钮规格时要找四五个地方。`.app-store-btn` 现在不影响画面，但选择器让人以为还有第二种下载按钮。

**ROI：中**

适合和删除 `icons.js` 同一次做。不要为此上图标组件库。

**最佳解决方案**

- 全站只留一种图标来源：一个隐藏的 SVG sprite，放在导航插入逻辑里，或一个只含实际用到的 path 的小对象（App Store、月亮、太阳、地球、箭头）。`theme.js` 用 `use href` 切换，不再写 path 字符串。
- 删除 `.app-store-btn` 及其在 JS 媒体查询、点击统计、内嵌浏览器里的选择器。下载按钮继续用 `.btn-primary`。首页两个按钮保持两份 HTML，它们只有父级不同。
- 内嵌浏览器按钮使用 `.btn-primary`，弹层颜色改用现有语义变量。独立的 `--inapp-*` 只保留遮罩透明度和步骤底色这种语义变量表达不了的值。
- App Store URL 常量化一处。`itms-apps` 跳转从这一个 URL 里取 id，去掉写死的默认 id。
- `getText()` 只调用 `MarkdI18n.getTranslation`。`inapp_title` 这类顶层键改成 `inapp.title`，和 `hero`、`nav` 一样。

### 8. 内嵌浏览器判断过宽，和设计说明不一致

**位置**

`assets/js/components/inapp-browser.js` 的 `isInAppBrowser()`。

目标应用（Instagram、微信、Facebook、TikTok、Line、Twitter）的判断是合理的。另外两条会扩大命中面：

- `/Line/i` 匹配任意包含 “line” 的 UA 片段，不要求独立词。
- 所有 iPhone / iPad UA，只要不含 `Safari` 且含 `AppleWebKit`，都当成内嵌浏览器。部分第三方 iOS 浏览器也是这种 WKWebView，用户点下载会先被拦截并尝试 `itms-apps://`。

选择器里 `a[href*="apps.apple.com"]` 已经覆盖前面的 `.btn-primary` 和 `.app-store-btn`。后两条是冗余。

`docs/superpowers/specs/2026-07-31-inapp-browser-download-prompt-design.md` 写检测在 `utils.js` / `main.js`，实现实际在 `inapp-browser.js`。同目录的 plan 是实现完成后的过程稿，和源码重复。

**影响范围**

只影响被判成内嵌浏览器的环境里的 App Store 链接。普通 Safari / 桌面浏览器不受影响。误判时用户会看到“在 Safari 中打开”的全屏层，并被尝试跳进 App Store scheme。

**ROI：中**

收紧判断是小改动。是否保留通用 WKWebView 条款是产品决定：只拦列出的社交 App，误拦更少；保留通用条款，能多盖住一些未知内嵌浏览器。

**最佳解决方案**

社交 App 用现有正则，`Line` 改为独立标记（例如 `(?:^|[^\w])Line(?:\/|\s)` 这一类边界），不要用裸的 `/Line/i`。通用 iOS WebView 条款单独注释清楚，或改为可开关的补充条件。点击绑定只保留 `a[href*="apps.apple.com"]`。

规格文档改成指向现有文件。`docs/superpowers/plans/` 里已经落地的实现稿可以归档或删除，避免和源码两套说明。

### 9. 繁体页面使用简体字体

这一条和 P0 的引导脚本是同一处修改，单独列出是因为即使用户语言判断正确，字体仍然错。

**位置**

三个页头和 `i18n.js` 的 `ensureCjkFont()`。CSS 的 `font-family` 也把 `"Noto Sans SC"` 固定写在西文系统字体后面。

**影响范围**

所有 `zh-TW` 用户。Noto Sans SC 按简体字形设计，繁体页面会混用简体字形，或对 SC 没有的字回退到系统字体，一段文字里出现两套字形。

**ROI：中**

和 `boot.js` 一起改即可。英文路径不加载这个样式表。

**最佳解决方案**

`zh` 加载 Noto Sans SC，`zh-TW` 加载 Noto Sans TC，并给 `<link id="font-noto-cjk">` 一个 id，切换语言时替换而不是只插入一次。CSS 字体栈写成 `"Noto Sans SC", "Noto Sans TC", ...`，谁被加载谁生效。

### 12. `localStorage` 失败时，页头和运行时的防护不一致

**位置**

三个页头把整个引导包在 `try/catch` 里，失败就保持 HTML 上的浅色和 `lang="en"`。`theme.js` 和 `i18n.js` 直接调用 `localStorage`，没有同样的保护。

`initApp()` 先初始化主题。若这里抛错，后面的语言初始化和按钮绑定不会执行。外层 `initializeApp()` 的 `try/catch` 只包住“注册 DOMContentLoaded”，包不住回调本身。

**影响范围**

存储被禁用或写入被拒绝的浏览器。正常桌面和手机浏览器不受影响。页脚按钮可能在这种环境里没有点击处理。

**ROI：低**

**最佳解决方案**

在 `boot.js` 里读完偏好后，把结果放在 `data-theme` 和 `data-lang` 上。`theme.js` / `i18n.js` 只在用户点击后再写 `localStorage`，写入单独 `try/catch`。启动路径不再直接碰可能抛错的存储 API。

### 13. 全站统计和隐私定位放在同一条加载路径上

**位置**

三个页面都在 `<head>` 同步配置 `gtag.js`，测量 ID `G-NCP461WXRW`。隐私页同样加载。没有同意层。

隐私政策正文说的是 App 可能收集匿名用量数据。站点这边的 Google 标签是另一件事：页面一打开就把请求发到 Google，包括正在阅读隐私政策的访问。

**影响范围**

全部页面，以及产品“默认私密”的表述。这不是死代码。若统计要保留，它是产品决定；若要和品牌一致，它是该拿掉或推迟到同意之后的加载项。

**ROI：中（取舍明确时）**

三份相同片段可以收进 `boot.js`，但那只解决重复，不解决请求本身。

**最佳解决方案**

先定产品决定。与品牌一致的做法是去掉站点 gtag。若业务要保留，至少不要在隐私页默认加载，并把“营销站使用 Google 分析”写进隐私政策。三份复制的片段收成一处，避免改 ID 时漏页。
